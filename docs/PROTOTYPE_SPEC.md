## 1. מטרה והיקף

לבנות **דגם עובד** של מערכת לניהול משרד עורכי דין קטן (2–3 עובדים) בתחום **דיני משפחה**. הדגם הוא הבסיס של המוצר עצמו, לא דגם זריקה. לכן הארכיטקטורה צריכה להיות נכונה מההתחלה.

**הדגם כולל:**
- כל המסכים של גרסה 1, עם פעולות אמיתיות מול מסד נתונים מקומי.
- נתוני דמה עשירים בעברית, שנראים כמו משרד אמיתי.
- מעבר בין משתמשים (מנהלת / עובד) כדי לראות הרשאות שונות.
- חיבורי Gmail, Calendar ו-Dropbox **במימוש דמה** בלבד, כדי לראות את חוויית השימוש.
- דלת כניסה לקליטת החלטות (Intake API) וסוכן דמה שמדגים אותה (סעיף 6.12). הסוכן האמיתי לא נבנה.
- מחולל מסמכים מתבניות, בלי AI (סעיף 6.14, שלב 7).

**הדגם לא כולל (אסור לבנות עכשיו):**
- כניסה אמיתית (Supabase Auth), Supabase, פריסה לאינטרנט.
- חיבור אמיתי לשירות חיצוני כלשהו.
- וואטסאפ, מחולל מסמכים עם AI, שעות וחיוב, חשבוניות. (שאלות פתוחות מול הלקוחה.)
- חיבור לתוכנת הנהלת חשבונות (חשבונית ירוקה / מורנינג). בבדיקה בלבד, תלוי בבדיקת ה-API שלהם.
- **גלישה לאתרי בתי המשפט (נט המשפט ואחרים), שמירת פרטי כניסה אליהם, והסוכן האוטומטי עצמו.** המערכת לא נכנסת לאתרים האלה ואין בה שדה לסיסמה שלהם. הסוכן הוא כלי חיצוני שעורך הדין מפעיל, והוא שולח החלטות ל-Intake API. לבדוק לפני מימוש אמיתי: תנאי השימוש של נט המשפט לגבי גישה אוטומטית; אישור לשלוח החלטות לספק AI (חיסיון, ותוכנית שבה הנתונים לא משמשים לאימון); ואחריות על דיוק הפירוק. לכן מועדים שנוצרו אוטומטית תמיד נשארים "ממתין לאימות".

## 2. מחסנית

| שכבה | בחירה | הערה |
| --- | --- | --- |
| מסגרת | Next.js (App Router) + TypeScript strict | Server Components + Server Actions |
| עיצוב | Tailwind CSS + ספריית קומפוננטות נגישה (למשל shadcn/ui) | לוודא תמיכה ב-RTL |
| מסד בדגם | SQLite דרך Prisma | קובץ מקומי `prisma/dev.db`, מחוץ ל-Git |
| מסד בהמשך | PostgreSQL ב-Supabase | המעבר יהיה בשינוי datasource, לכן אין להשתמש ביכולות ייחודיות ל-SQLite |
| אימות קלט | zod | בכל Server Action |
| בדיקות | Vitest | לשכבת השירותים וההרשאות |
| גופן | גופן עברי מ-next/font (למשל Heebo או Assistant) | |

**הערה על Enums:** כדי שהמעבר ל-Postgres יהיה פשוט, שדות סטטוס יישמרו כ-String במסד. הערכים המותרים מוגדרים כקבועי TypeScript ב-`src/shared/constants.ts` ונאכפים ב-zod.

## 4. משתמשים, תפקידים והרשאות

שלושה תפקידים: `MANAGER` (עורכת הדין), `EMPLOYEE` (עובד/ת) ו-`SECRETARY` (מזכירות).

### בורר משתמשים (דגם בלבד)
בסרגל העליון: "צפייה בתור: [שם] ▾" עם תג **מצב פיתוח**. הבחירה נשמרת ב-cookie. זה לא אימות אמיתי, אבל **כל ההרשאות נאכפות בשרת לפי המשתמש שנבחר**, בדיוק כמו שיהיה עם כניסה אמיתית.

### משתמש מערכת "קליטה אוטומטית"
משתמש עם `isSystem = true` שנוצר ב-seed (שלב 6), ומשמש כ-`createdById` / `actorId` של משימות, מועדים, אירועי משימה ו-AuditEvent שנוצרים מה-Intake API. הוא **לא יכול להתחבר ולא מופיע בשום רשימת בחירה**: לא בבורר המשתמשים, לא בבחירת אחראי או עובד, ולא ברשימת המשתמשים בהגדרות. נאכף בשירות, לא רק בממשק. בהיסטוריה ובציר הזמן הוא מוצג בשם "קליטה אוטומטית".

- המזכירות עורכת פרטי לקוח, סטטוס קשר ופרטי תיק, אבל **לא את שדה החסמים** (`blockers`), שנשאר למנהלת בלבד.
- בעתיד, כשיתווסף מודול חיוב, המזכירות יראו אותו. כרגע אין מה להציג.
- **בדיקות:** הטבלה כולה, כולל ניסיונות ישירים לשרת בפעולות האסורות. כל שורה נבדקת בשלב שבו הפעולה נבנית.

**חובה:** כל קריאה ושינוי נבדקים בשירות. גם גישה ישירה לכתובת (`/cases/[id]` של תיק שאינו שלו, או `/api/files/[id]`) מחזירה "אין הרשאה" ולא את הנתונים. הסתרת כפתורים בלבד אינה הרשאה.

### שדות לקליטה אוטומטית (שלב 6) ולסינון לפי מקור (שלב 4א)
- **Decision:** `autoIngested` (boolean, מציג את התג "נקלטה אוטומטית"), `intakeSource?` (שם האתר), `intakeSourceUrl?`, `externalId?` (ייחודי לפי orgId, למניעת כפילויות), `apiKeyId?`, `pendingItems?` (JSON: הצעת הפירוק של החלטה "לשיוך", נשמרת עד לשיוך).
- **Task, Deadline:** `autoCreated` (boolean, מציג את התג "אוטומטי"). Task מקבלת גם `inboxItemId?`, כדי שהסינון "מקור" (החלטה / חומר חדש / ידני) יהיה אפשרי.

### ערכים בעברית (`src/shared/constants.ts`)
- **caseType:** גירושין, מזונות, משמורת וזמני שהות, רכוש ואיזון משאבים, הסכם ממון, צוואות וירושות, אפוטרופסות, אחר.
- **court:** בית משפט לענייני משפחה, בית הדין הרבני, בית משפט מחוזי, בית המשפט העליון, אחר.
- **InboxItem.kind:** החלטת בית משפט, כתב טענות של צד שכנגד, מסמך מהלקוח, מכתב, אחר.
- **Client.contactStatus** (רשימה הניתנת להגדרה `CONTACT_STATUS`): פעיל, ממתין לתגובת הלקוח, לא זמין, הסתיים הטיפול.
- **Decision.reviewStatus:** לא נבדקה (`PENDING`), נבדקה (`REVIEWED`). קבוע בקוד, לא רשימה הניתנת להגדרה.
- **InboxItem.readStatus:** `NAME_ONLY` מוצג "זוהה לפי שם הקובץ בלבד – התוכן לא נקרא".
- **Task status:** ראו סעיף 7.
- **CaseNote.kind:** שיחת טלפון (`CALL`), פגישה (`MEETING`), הערה (`NOTE`).
- **TEMPLATE_TYPE** (רשימה הניתנת להגדרה, שלב 7): תביעה למזונות, תביעה למשמורת, תביעה רכושית, תביעת גירושין, כתב הגנה, בקשה בכתב, כתב תגובה, תשובה לתגובה, סיכומים, תצהיר, מכתב, הסכם שכר טרחה.

## 6. מסכים

### מבנה כללי
- `<html lang="he" dir="rtl">`. תפריט צד מימין: לוח בקרה · לקוחות · תיקים · משימות · החלטות · חומר חדש · מסמכים · יומן ומועדים · סל מחזור · הגדרות, ופריט קבוע "קליטת החלטה" (פותח חלונית, סעיף 6.11).
- בטלפון התפריט נפתח מכפתור. טבלאות הופכות לכרטיסים ברוחב קטן.
- עיצוב נקי: כחול כהה, לבן ואפור. **כתום** = החזרה לתיקון והוספת חומר חדש. **אדום** = מחיקה. **ירוק** = הושלם/אומת. צבע תמיד מלווה בטקסט.
- כל רשימה מבחינה בין: טוען / ריק ("אין עדיין תיקים") / שגיאה ("לא הצלחנו לטעון. נסו שוב"). שגיאה לעולם לא מוצגת כרשימה ריקה.

### 6.1 לוח בקרה `/`
**בראש המסך: "דורש טיפול".** שלושה אזורים זה לצד זה (בטלפון: זה מתחת לזה), לפני כרטיסי המספרים:

| אזור | מנהלת | עובד |
| --- | --- | --- |
| **מועדים קרובים** | 7 הימים הקרובים, קודם מה שעבר ולא סומן כבוצע, ואחר כך מה שלא אומת | אותו דבר, רק בתיקים שלו |
| **החלטות לטיפול** | החלטות `PENDING`, והחלטות שנבדקו ואין להן מועד (גם אם יש להן משימה), אלא אם סומנו "לא נדרש מועד" | החלטות בתיקים שלו שאין להן משימה |
| **ממתין לי** | משימות שממתינות לבדיקה שלה | משימות שהוחזרו אליו לתיקון |

- בכל אזור עד 5 פריטים, עם קישור "לכל הרשימה".
- כל פריט מציג את שם התיק ותאריך, ולחיצה מובילה ישירות לפריט.
- אזור ריק מציג הודעה חיובית ("אין החלטות שממתינות לטיפול"), ולא אזור ריק.

- (שלב 6) אזור **"נקלט הבוקר"**: ראו סעיף 6.12 ב.

**מתחת: כרטיסי סיכום**, וכל כרטיס לחיץ ומוביל לרשימה המסוננת:
- תיקים עם חסם (`blockers` לא ריק).
- מועדים ב-7 הימים הקרובים (דחופים מודגשים, מועדים שלא אומתו מסומנים).
- משימות באיחור.
- למנהלת: ממתינות לבדיקה. לעובד: הוחזרו אליי לתיקון.
- חומר חדש שלא נצפה (דחוף קודם).
- מתחת: רשימת "השבוע שלי" – מועדים ומשימות לפי תאריך.

### 6.2 לקוחות `/clients`, `/clients/[id]`
- רשימה עם חיפוש (שם, ת"ז, טלפון) וסינון סוג וסטטוס קשר (עם עמודה "סטטוס קשר").
- כרטיס לקוח: פרטים, סטטוס קשר, אנשי קשר, הערות פנימיות, רשימת התיקים שלו.
- יצירה ועריכה בחלונית (מנהלת בלבד). אי אפשר למחוק לקוח שיש לו תיקים פעילים (הודעה ברורה).

### 6.3 תיקים `/cases`, `/cases/[id]`
- רשימה: חיפוש (כותרת, שם לקוח, מספר פנימי, מספר הליך), סינון לפי סטטוס, סוג, אחראי.
- דף תיק עם כותרת עליונה (לקוח, סוג, ערכאה, מספר הליך, צד שכנגד, אחראי, סטטוס) ולשוניות:
  - **סקירה:** סיכום מצב, פעולה הבאה, חסמים (בולט אם לא ריק; עריכה למנהלת בלבד, עם נעילה אופטימית ו-AuditEvent), עובדים משויכים, המועד הקרוב, משימות פתוחות, ושלושת התיעודים האחרונים.
  - **משימות** של התיק.
  - **מסמכים** של התיק (כולל לשונית משנה "Dropbox – דמה").
  - **מועדים** של התיק.
  - **החלטות** של התיק: לפי תאריך החלטה, חדש למעלה, עם תג "לא נבדקה" ומספר המועדים והמשימות שנוצרו.
  - **מיילים** (דמה): מיילים משויכים + "מיילים מוצעים לשיוך".
  - **תיעוד:** שיחות, פגישות והערות (סעיף 6.13).
  - **היסטוריה:** AuditEvent של התיק.

### 6.4 משימות `/tasks`, `/tasks/[id]`
- לשוניות: פתוחות · המשימות שלי · ממתינות לבדיקה · הושלמו · **לפי אדם** (מנהלת בלבד, להלן).
- **אצל מי עכשיו:** בכל משימה מוצג מי מחזיק בה, לפי המצב: `ASSIGNED` / `CHANGES_REQUESTED` → העובד המוקצה; `IN_REVIEW` → המנהלת (ממתין לבדיקה שלה); `OPEN` → מי שהוקצה לה, ואם אין מוקצה, מי שיצר אותה; `COMPLETED` → אף אחד.
- **מנהלת יכולה להשאיר משימה אצלה:** assignee = המנהלת, בסטטוס `OPEN`. משימה שהיא יוצרת בלי בחירת עובד שייכת לה. שיוך לעובד (OPEN → ASSIGNED) נשאר כמו בסעיף 7.
- **סרגל סינון** מעל כל לשונית: אצל מי (כולם / אני / אדם מסוים), תיק, סטטוס, עדיפות, מועד יעד (באיחור / היום / השבוע / טווח תאריכים), מקור (החלטה / חומר חדש / ידני). הסינון נשמר בכתובת (query string), עם כפתור "ניקוי סינון". עובד רואה את אותו סינון, אבל רק על המשימות שמותר לו לראות, והסינון נאכף בשירות.
- **לשונית "לפי אדם" (עומס צוות, מנהלת):** עמודה לכל אחד בצוות, כולל המנהלת, עם מספר המשימות שאצלו עכשיו, כמה באיחור וכמה הוחזרו לתיקון. בכל עמודה רשימת המשימות שאצלו לפי מועד יעד, באיחור מודגש באדום (עם טקסט). לחיצה על שם פותחת את הרשימה המסוננת לאותו אדם. בטלפון: כרטיס לכל אדם, זה מתחת לזה.
- **אסמכתה בסיום:** בחלונית הסיום, לצד סיכום הביצוע (חובה), קובץ אסמכתה אופציונלי (אישור הגשה, מכתב שנשלח, צילום מסך). נשמר כ-Document עם `taskId` ומקושר לאירוע ה-COMPLETED (`TaskEvent.documentVersionId`). בדף המשימה ובלשונית "הושלמו": תג "יש אסמכתה" / "ללא אסמכתה" (לפי אירוע ה-COMPLETED האחרון), וסינון "ללא אסמכתה". פתיחה מחדש לא מוחקת את האסמכתה.
- דף משימה: פרטים, הוראות, קבצים מצורפים, ציר זמן של TaskEvent (מי, מה, מתי, הערה, קובץ).
- כפתורי פעולה לפי מצב ותפקיד בלבד (סעיף 7).

### 6.5 חומר חדש `/inbox`
- רשימה: קודם לא נצפה, ובתוכו דחוף קודם. בכל פריט: סוג, כותרת, תיק או "לשיוך", מי הוסיף ומתי, מספר קבצים, תג "חדש"/"נצפה".
- כפתור כתום "הוספת חומר חדש": סוג, תיק (או "לשיוך"), כותרת, הערה, קישור למקור, קבצים (עד 10), "דחוף".
- דף פריט: הערה, שיוך (אפשר לשייך לתיק), קבצים לפתיחה והורדה. פעולות: "יצירת משימה מהפריט", "יצירת מועד מהפריט" (משלב 5), ו"יצירת החלטה מהפריט" לפריט מסוג "החלטת בית משפט" (משלב 5).
- פריט שנקלט מ-Dropbox (סעיף 8): מציג "הצעה: תיק X – אישור / שינוי" כשיש התאמה אחת, ותג readStatus. פריט בלי התאמה, או עם יותר מאחת, נכנס ל"לשיוך", וזה תור הבדיקה (אין תור נפרד).
- מנהלת: "סמן שצפיתי". רק אחרי סימון מופיע "מחיקה" (אדום, חלונית אישור).
- לשונית "סל מחזור" בתוך האזור.

### 6.6 מסמכים `/documents`
- חיפוש בכל המסמכים שהמשתמש מורשה לראות: שם, תיק, מקור, מי העלה, תאריך.
- העלאה: PDF, DOCX, XLSX, TXT, JPG, PNG. עד 10 קבצים, 20MB לקובץ, 40MB בסך הכול. בדיקת סוג אמיתי (חתימת קובץ) וגודל בשרת. שם קובץ עברי נשמר ומוצג נכון.
- גרסאות: "העלאת גרסה חדשה" לאותו מסמך. כל הגרסאות נשמרות ונגישות.
- הורדה רק דרך `/api/files/[versionId]` עם בדיקת הרשאה. אין קישור ישיר לקובץ בדיסק.

### 6.7 יומן ומועדים `/calendar`
- תצוגות: רשימה (ברירת מחדל), שבוע, חודש.
- סינון לפי סוג, אחראי, "לא אומת".
- טופס מועד: תיק, סוג, כותרת, תאריך, שעה (לדיון), ערכאה/מקום, מקור (טקסט), קישור להחלטה (אופציונלי, מתוך החלטות התיק; תאריכי ההחלטה וההמצאה מוצגים ממנה ואינם שדות של המועד), אחראי, תזכורת X ימים לפני.
- המערכת **לא מחשבת** מועדים משפטיים. מועד חדש נוצר במצב "ממתין לאימות עו"ד". רק מנהלת מסמנת "אומת". מתחת לשדה התאריך: "יש לחשב לפי ההחלטה, תאריך ההמצאה והכללים החלים, ולאשר."
- בשמירה: קריאה ל-CalendarAdapter (mock) שמחזיר מזהה אירוע. בתצוגה: "סונכרן ליומן גוגל (דמה)".

### 6.8 סל מחזור `/trash`
- כל מה שנמחק: משימות, מסמכים, חומר חדש, מועדים, לקוחות ותיקים. מי מחק ומתי.
- שחזור מחזיר למצב הקודם (משימה חוזרת לסטטוס שנשמר ב-statusBeforeTrash) עם כל הקבצים.

### 6.9 הגדרות `/settings`
- **משתמשים:** רשימה ותפקידים (צפייה בלבד בדגם).
- **חיבורים:** כרטיס לכל ספק עם מצב (`לא מוגדר` / `מחובר – דמה`), כפתור "חיבור (דמה)" ו"ניתוק". הסבר קצר מה כל חיבור יעשה בגרסה האמיתית. בכרטיס Dropbox, למנהלת: "סימולציה: קובץ חדש הגיע ל-Dropbox" (סעיף 8).
- **ייצוא `/settings/export`** (מנהלת בלבד): לקוחות, תיקים, משימות, תיעוד בתיק, מועדים, החלטות, חומר חדש (בלי קבצים) ורשימת מסמכים (מטא-דאטה בלבד). כל ייצוא הוא קובץ CSV נפרד (בלי ZIP ובלי ספרייה חיצונית). UTF-8 עם BOM, כותרות בעברית, תאריכים `YYYY-MM-DD`. מסומן: "הייצוא אינו כולל את הקבצים עצמם ואינו תחליף לגיבוי." עובר דרך שירות `export` עם בדיקת הרשאה וכותב AuditEvent (מי, מתי, אילו טבלאות, כמה שורות). רשומות שנמחקו לסל לא נכללות. תא שמתחיל ב-`=`, `+`, `-` או `@` מנוטרל בהקדמת תו, נגד הזרקת נוסחאות ב-Excel.

### 6.10 החלטות `/decisions`, `/decisions/[id]`
- **ההחלטה היא מקור המועדים.** תאריכי ההחלטה וההמצאה שייכים ל-Decision. מועד ומשימה שנוצרו מהחלטה מקושרים אליה (`decisionId`), ומועד מציג את תאריכיה מתוכה.
- רשימה כללית: כל ההחלטות שהמשתמש מורשה לראות, עם סינון "לא נבדקה" וערכאה.
- דף החלטה: כל השדות, המועדים והמשימות המקושרים, היסטוריה (AuditEvent).
- מתוך החלטה: "יצירת מועד" ו"יצירת משימה". השיוך לתיק, ההוראה (obligation) והקישור להחלטה מועתקים. אפשר כמה מועדים וכמה משימות להחלטה אחת. יצירת משימה לא מסמנת את החובה כבוצעה.
- מועד שנוצר מהחלטה נוצר במצב "ממתין לאימות", והמערכת לא מחשבת אותו (סעיף 6.7).
- "נבדקה" מסומן רק על ידי מנהלת. עובד רואה ויוצר (PENDING) בתיקים שלו, ועורך החלטה PENDING שיצר בעצמו.
- אסמכתת המצאה: תיאור טקסט, ואפשר גם קובץ (Document).
- "לא נדרש מועד": סימון של מנהלת בלבד על החלטה, שמוציא אותה מהאזור "החלטות לטיפול" בלוח הבקרה כשאין לה מועד. אפשר לבטל את הסימון.
- החלטה שנקלטה "לשיוך" (בלי תיק) לא מאפשרת יצירת מועד או משימה עד שיוך לתיק. החלטה ומסמך בלי תיק גלויים רק ליוצר ולמנהלת, כמו חומר חדש.

### 6.11 קליטת החלטה מהירה
- פריט קבוע בתפריט, לכל המשתמשים, בתיקים שהם מורשים להם. פותח חלונית אחת:
  - קובץ ההחלטה (PDF או תמונה), חובה.
  - תיק: בחירה מרשימה, עם חיפוש לפי מספר הליך, או "לשיוך".
  - תאריך החלטה (חובה), כותרת קצרה, תאריך המצאה (אופציונלי), הערה.
- בשמירה נוצרת Decision במצב `PENDING` עם הקובץ כ-`sourceDocumentId`. אם נבחר "לשיוך", נוצר גם פריט חומר חדש מסוג "החלטת בית משפט" שמקושר להחלטה (`inboxItemId`), כדי שייכנס לתור הבדיקה.
- אחרי השמירה עוברים לדף ההחלטה, שם ממלאים את הסעיף האופרטיבי ומה צריך לבצע, ויוצרים מועדים ומשימות (לפי ההרשאות בסעיף 4).

### 6.12 קליטה יומית של החלטות (Intake API) ופירוקן
**רקע:** בכל בוקר סוכן AI חיצוני, שעורך הדין מפעיל עם הכניסה שלו, מאתר החלטות חדשות באתרי בתי המשפט, מפרק כל אחת לפריטי עבודה ושולח אותה למערכת. עורך הדין מוחק את מה שלא רלוונטי. זו יכולת מרכזית.

**עקרון המבנה:** המערכת לא נכנסת לאתרי בתי המשפט ולא שומרת פרטי כניסה אליהם. אין בה שדה לסיסמה ואין בה קוד שמתחבר לאתרים האלה. החלטות נכנסות **רק** דרך ה-Intake API. הסוכן עצמו לא נבנה בדגם.

**א. Intake API (שלב 6)**
- `POST /api/intake/decisions`, עם מפתח API לכל ארגון. המפתח נוצר ומבוטל במסך ההגדרות (מנהלת בלבד), נשמר כ-hash ומוצג פעם אחת בלבד.
- למפתח הרשאה אחת: קליטת החלטות. הוא לא יכול לקרוא, לערוך או למחוק שום דבר אחר (ניסיון GET נחסם).
- גוף הבקשה (נבדק עם zod):
  - `externalId`: מזהה ההחלטה במקור (או hash של הקובץ), למניעת כפילויות.
  - `source`: שם האתר; `sourceUrl` (אופציונלי).
  - `proceedingNumber`, `court`, `decisionDate`, `title`, `operativeText` (אופציונלי), `fileBase64` + `fileName` (אופציונלי, באותן בדיקות סוג וגודל של סעיף 6.6).
  - `items[]`: הצעת פירוק. כל פריט: `kind` (`HEARING` / `LEGAL_DEADLINE` / `INTERNAL_TARGET` / `TASK`), `description`, `date`, `time`, `location`.
- מה המערכת עושה:
  - **כפילות:** אותו `externalId` שוב → מחזירה את ההחלטה הקיימת ולא יוצרת כלום.
  - **שיוך לתיק** לפי מספר ההליך. אם אין התאמה אחת ברורה → ההחלטה נשמרת "לשיוך", ו**הפריטים לא נוצרים** עד שמשייכים תיק. הצעת הפירוק נשמרת על ההחלטה (`pendingItems`), ובשיוך לתיק (בידי מנהלת) הפריטים נוצרים אוטומטית, באותה טרנזקציה של השיוך ובאותם כללים.
  - נוצרת Decision במצב `PENDING`, עם התג "נקלטה אוטומטית", המקור והקובץ.
  - **משימות** נוצרות ומוקצות **למנהלת** (עורך הדין הראשי), עם `decisionId` והתג "אוטומטי".
  - **דיונים ומועדים** נוצרים במצב **"ממתין לאימות"**. המערכת לעולם לא מסמנת "אומת" לבד.
  - הכול בטרנזקציה אחת. כל קליטה נרשמת ב-AuditEvent עם המקור ועם מזהה המפתח.
- תשובה: מזהה ההחלטה, האם הייתה כפילות, ומה נוצר.

**ב. "נקלט הבוקר" בלוח הבקרה (שלב 6)**
- אזור שמציג את ההחלטות שנקלטו מאז אתמול, ולכל אחת מספר המשימות והמועדים שנוצרו ממנה.
- מחיקת משימה או מועד שנוצרו אוטומטית שולחת אותם לסל המחזור, כמו כל מחיקה אחרת.
- כפתור "אישור הכול" להחלטה: מסמן אותה "נבדקה", ואת המועדים שלה "אומת". רק למנהלת, עם חלונית אישור.

**ג. פירוק ידני (שלב 5)**
אותה טבלת פירוק משמשת גם ידנית, להחלטה שנקלטה בכפתור "קליטת החלטה":
- **למנהלת בלבד**, כי הפירוק יוצר גם משימות. עובד ומזכירות ממשיכים ליצור מועד בודד לפי סעיף 4.
- בדף ההחלטה: **"פירוק ההחלטה"**, שפותח טבלה לעריכה, שורה לכל פריט: סוג, תיאור, תאריך, שעה ומקום, אחראי.
- "יצירת כל הפריטים": הכול בטרנזקציה אחת. כישלון באחד מבטל את כולם.
- כל פריט מציג "נוצר מהחלטה מיום X", וההחלטה מציגה את כל הפריטים שנוצרו ממנה.

**ד. סוכן דמה לבדיקה (שלב 6)**
- סקריפט `npm run demo:intake`, ששולח ל-API שלוש החלטות דמה עם הצעת פירוק: אחת עם התאמה לתיק, אחת "לשיוך", ואחת כפולה. מראה את כל הזרימה בלי סוכן אמיתי.

**בדיקות:** מפתח לא תקין או מבוטל → 401 ושום דבר לא נוצר; אותו `externalId` פעמיים → החלטה אחת; מספר הליך שלא תואם → החלטה "לשיוך" ובלי פריטים; פירוק עם פריט לא תקין → אף פריט לא נוצר; מועד שנוצר אוטומטית לא מסומן "אומת"; המפתח לא יכול לקרוא נתונים.

### 6.13 תיעוד בתיק (שלב 4א)
- לשונית **"תיעוד"** בדף התיק: רשימה לפי `occurredAt`, חדש למעלה, עם סינון לפי סוג. כפתור "תיעוד חדש".
- מי יכול: כל מי שמורשה לתיק יכול ליצור. עריכה: היוצר, תוך 24 שעות, או מנהלת בכל זמן. מחיקה לסל: מנהלת.
- כל יצירה ועריכה כותבות AuditEvent עם `caseId`.
- בלשונית "סקירה" של התיק: שלושת התיעודים האחרונים.

### 6.14 תבניות מסמכים (שלב 7)
מחולל מסמכים **בלי AI**: תבנית עם שדות שמתמלאים אוטומטית מפרטי התיק.
- **שדות לשילוב בתבנית:** `{{client.fullName}}`, `{{client.idNumber}}`, `{{client.address}}`, `{{case.title}}`, `{{case.courtCaseNumber}}`, `{{case.court}}`, `{{case.opposingParty}}`, `{{case.opposingCounsel}}`, `{{office.name}}`, `{{user.name}}`, `{{today}}`.
- **זרימה:** (1) בדף התיק: "יצירת מסמך מתבנית" ← בחירת תבנית. (2) תצוגה מקדימה; שדה ריק מסומן בבירור `[חסר: מספר הליך]` ולא נעלם. (3) "יצירה": נוצר קובץ Word (DOCX) בעברית, מימין לשמאל, שנשמר כ-Document בתיק עם `source = TEMPLATE` ותג "טיוטה". (4) אפשר להוריד, לערוך ב-Word ולהעלות גרסה חדשה (מנגנון הגרסאות משלב 4ב).
- **ניהול תבניות:** מסך `/settings/templates`, למנהלת בלבד: יצירה, עריכה, השבתה. תבנית מושבתת לא מופיעה בבחירה.
- **נתוני דמה:** 4 תבניות קצרות, כל אחת מסומנת בראשה "תבנית דמה – אינה לשימוש משפטי".
- **טכני:** יצירת DOCX דרך ספרייה מוכרת. לבדוק בתיעוד הרשמי את התמיכה בעברית ובכיוון מימין לשמאל, ולהציג למפתחת לפני התקנה.
- **בדיקות:** מילוי שדות, שדה חסר, תבנית מושבתת, הרשאות.

## 7. זרימת משימה (state machine)

מצבים: `OPEN` (פתוחה) · `ASSIGNED` (אצל העובד) · `IN_REVIEW` (ממתינה לבדיקה) · `CHANGES_REQUESTED` (הוחזרה לתיקון) · `COMPLETED` (הושלמה).

| מעבר | מי | תנאים |
| --- | --- | --- |
| OPEN → ASSIGNED | מנהלת | בחירת עובד שחבר בתיק. מעדכן את **אותה** משימה, לא יוצר חדשה |
| ASSIGNED → IN_REVIEW | העובד המוקצה | חובה קובץ חדש **או** הערת מענה לא ריקה |
| CHANGES_REQUESTED → IN_REVIEW | העובד המוקצה | אותו תנאי |
| IN_REVIEW → CHANGES_REQUESTED | מנהלת | הערת תיקון חובה. כפתור **כתום** "החזרה לעובד לתיקון". אפשר לצרף גרסה |
| IN_REVIEW → COMPLETED | מנהלת | סיכום ביצוע חובה. קובץ אסמכתה אופציונלי |
| ASSIGNED / OPEN → COMPLETED | מנהלת | סיום ישיר, עם סיכום חובה. קובץ אסמכתה אופציונלי |
| COMPLETED → OPEN או ASSIGNED | מנהלת | "פתיחה מחדש" עם סיבה חובה. ההיסטוריה נשמרת |
| כל מצב → סל מחזור | מנהלת | כפתור **אדום**. חלונית: "למחוק את המשימה '[שם]'?" עם "כן, מחק" ו"ביטול". **המיקוד מתחיל על ביטול.** Esc = ביטול. שומר statusBeforeTrash |

- משימה שהמנהלת מחזיקה בעצמה (assignee = המנהלת) נשארת `OPEN` עד סיום ישיר (OPEN → COMPLETED) או שיוך לעובד. משימה שנוצרה אוטומטית מ-Intake מתחילה כך.
- כל מעבר כותב TaskEvent ו-AuditEvent באותה טרנזקציה.
- מעבר לא חוקי נדחה בשירות עם הודעה בעברית, גם אם נשלח ישירות.
- נעילה אופטימית: עדכון עם `version` ישן נדחה בהודעה "המשימה עודכנה בחלון אחר. רעננו את הדף."
- כפתורי שליחה ננעלים בזמן שליחה (מניעת לחיצה כפולה).

## 8. חיבורים במימוש דמה

לכל ספק ממשק ב-`src/server/integrations/<provider>/types.ts` ומימוש `mock.ts`. הממשק מתוכנן כך שהמימוש האמיתי יחליף את ה-mock בלי לגעת בשאר הקוד.

- **Gmail (קריאה בלבד):** `listMessages(userId, query)`, `getMessage(id)`. קורא מטבלת MockEmail. בדף תיק: מיילים "מוצעים" = מיילים שהשולח או הנמען תואם למייל של הלקוח או של עו"ד הצד שכנגד, או שהנושא מכיל את מספר ההליך. כפתורים: "שייך לתיק" ו"העבר לחומר חדש" (יוצר InboxItem עם `source = EMAIL` והמייל כהערה).
- **Calendar:** `upsertEvent(deadline)` ו-`deleteEvent(externalId)`. ה-mock מחזיר מזהה `mock-...` וכותב AuditEvent "סונכרן ליומן (דמה)".
- **Dropbox:** `listFolder(path)`. ה-mock מחזיר רשימת קבצים קבועה לכל תיק לפי `dropboxFolderPath`. מוצג בלשונית "Dropbox – דמה", לקריאה בלבד.

### קליטת מסמכים חדשים מ-Dropbox (דמה)
1. בדגם: כפתור למנהלת במסך החיבורים, "סימולציה: קובץ חדש הגיע ל-Dropbox", עם בחירה מכמה קבצי דמה מוכנים. מסומן "דמה".
2. ה-DropboxAdapter מחזיר את הקובץ: שם, נתיב, מזהה, גרסה.
3. **ניסיון זיהוי** (בדגם: לפי שם הקובץ והנתיב בלבד):
   - מספר הליך או מספר פנימי של תיק בשם או בנתיב: הצעת שיוך לתיק.
   - התיקייה ממופה לתיק (`Case.dropboxFolderPath`): הצעת שיוך לתיק.
   - המילה "החלטה" בשם הקובץ: הצעת סוג "החלטת בית משפט".
4. נוצר פריט חומר חדש עם `source = DROPBOX`, מזהה הקובץ והגרסה, `suggestedCaseId` ו-`matchReason` (למשל "מספר ההליך מופיע בשם הקובץ"). התאמה אחת ברורה: "הצעה: תיק X – אישור / שינוי". אין התאמה או יש יותר מאחת: הפריט נכנס ל"לשיוך", וזה תור הבדיקה.
5. מהפריט: "יצירת משימה", "יצירת החלטה" (אם הסוג הוא החלטה), "יצירת מועד".
6. **מניעת כפילויות:** אותו מזהה קובץ ואותה גרסה לא נקלטים פעמיים.
7. `readStatus` תמיד `NAME_ONLY` בדגם, ומוצג בתג: "זוהה לפי שם הקובץ בלבד – התוכן לא נקרא".
8. **מחוץ לדגם:** קריאת התוכן בפועל (חילוץ טקסט, OCR) וזיהוי לפי תוכן (בגרסה האמיתית: שירות OCR שייבחר אחרי בדיקת עלות ופרטיות), ומעקב אוטומטי אחר שינויים ב-Dropbox (webhook או סריקה מתוזמנת).
- כל מקום שמציג נתוני חיבור מסומן בתג "דמה".

## 10. בדיקות (Vitest)

לפחות:
- כל מעבר במכונת המצבים: מותר למי שצריך, נדחה לכל השאר.
- הגשה לבדיקה בלי קובץ ובלי הערה נדחית.
- החזרה לתיקון בלי הערה נדחית. סיום בלי סיכום נדחה.
- עובד לא רואה תיק שאינו חבר בו (שירות התיקים, המסמכים וההורדה).
- מחיקת חומר חדש לפני "צפיתי" נדחית. עובד לא יכול לסמן "צפיתי".
- מחיקה ושחזור של משימה מחזירים את הסטטוס הקודם ואת הקבצים.
- עדכון עם version ישן נדחה.
- סיום משימה עם אסמכתה ובלעדיה; פתיחה מחדש משאירה את האסמכתה; סינון "ללא אסמכתה".
- החלטות: עובד לא רואה החלטה בתיק שאינו שלו, יוצר רק PENDING, לא מסמן "נבדקה"; יצירת משימה מהחלטה לא משנה את ההחלטה; מועד מההחלטה נוצר ממתין לאימות.
- קליטת החלטה: עם תיק ו"לשיוך" (נוצר גם פריט חומר חדש מקושר).
- קליטה מ-Dropbox: התאמה אחת, בלי התאמה, יותר מהתאמה אחת, וכפילות (אותו מזהה וגרסה).
- תפקיד מזכירות: כל שורה בטבלה (סעיף 4), כולל ניסיונות ישירים לשרת בפעולות האסורות.
- תיעוד בתיק: יצירה, עריכה בתוך 24 שעות ואחריהן (יוצר מול מנהלת), מחיקה למנהלת בלבד, AuditEvent עם caseId.
- "אצל מי עכשיו" נכון בכל אחד מחמשת המצבים.
- עובד שמסנן לפי עובד אחר לא מקבל משימות שאינן שלו (נבדק בשירות). הספירות במסך "לפי אדם" תואמות לרשימה המסוננת.
- Intake API ופירוק ידני: סעיף 6.12. תבניות מסמכים: סעיף 6.14.
- ייצוא: כולל תיעוד בתיק (CaseNote). הייצוא מכסה את כל המידע העסקי של המשרד.
- ייצוא: מנהלת בלבד, BOM וכותרות בעברית, ניטרול נוסחאות, AuditEvent עם ספירת שורות.

## 11. שלבי בנייה

בסוף כל שלב: האפליקציה רצה, `npm run lint`, `npm run typecheck` ו-`npm test` עוברים, `docs/STATUS.md` מעודכן, ומדווחים למפתחת **מה לבדוק בדפדפן**. ואז עוצרים ומחכים לאישור.

2. **לקוחות ותיקים:** רשימות, חיפוש, סינון, יצירה ועריכה, דף תיק עם לשונית סקירה והיסטוריה. הרשאות עובד.
3. **משימות:** כל הזרימה מסעיף 7, ציר זמן, מחיקה לסל ושחזור, בדיקות.
4א. **משימות לפי אדם, תיעוד ותפקידים:** "אצל מי עכשיו", משימה שנשארת אצל המנהלת, לשונית "לפי אדם" וסרגל סינון ב-`/tasks` (סעיף 6.4); תיעוד בתיק (סעיף 6.13); תפקיד מזכירות (סעיף 4) לפעולות שכבר קיימות; סטטוס קשר ללקוח וחסמים בתיק; בדיקות.
4ב. **מסמכים וחומר חדש:** StorageAdapter, העלאה ואימות, גרסאות, הורדה מאובטחת, אזור חומר חדש מלא (כולל השדות `source`, `suggestedCaseId`, `matchReason`, `readStatus`), אסמכתה בסיום משימה (וקובץ בהגשה לבדיקה), בדיקות. כולל הפעולות של המזכירות בחומר חדש.
5. **מועדים, החלטות ולוח בקרה:** יומן (רשימה, שבוע, חודש), אימות מועדים, מודול החלטות (כולל העברת תאריכי ההחלטה וההמצאה מ-Deadline ל-Decision), קליטת החלטה מהירה, **פירוק ידני של החלטה (סעיף 6.12 ג)**, לוח בקרה אמיתי עם "דורש טיפול" וכרטיס "תיקים עם חסם". כולל הפעולות של המזכירות במועדים ובהחלטות.
6. **חיבורי דמה, קליטה אוטומטית וגימור:** Gmail, Calendar ו-Dropbox במימוש דמה, כולל סימולציית קליטה מ-Dropbox, מסך חיבורים, **Intake API, מפתחות API, "נקלט הבוקר" וסוכן דמה (סעיף 6.12 א, ב, ד)**, ייצוא CSV, סל מחזור כללי, מעבר רספונסיבי (360 / 768 / 1440), נגישות מקלדת בחלוניות.
7. **תבניות מסמכים:** סעיף 6.14. לפני ההתקנה של ספריית ה-DOCX מציגים למפתחת את תוצאות בדיקת התיעוד.
